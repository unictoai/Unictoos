# Unictoos v0.4.3 Enhancement Implementation

## Scope

This release implements the locally verifiable portion of the attached Unictoos enhancement brief on top of the stable v0.4.2 streaming baseline. The implementation preserves the mobile-first Compose workflow, Keystore-backed credentials, foreground-service ownership of capture, and generation-safe RootEncoder lifecycle.

## Implemented locally

| Area | Implementation | Verification boundary |
|---|---|---|
| Local analytics | SQLiteOpenHelper database with bounded `streaming_sessions` table, recent-session query, and comparison math | JVM policy tests; Android database behavior still benefits from device testing |
| Scene management | Persisted `SourceGroup`, per-source group IDs, transition mode, and bounded transition duration; mobile presentation controls and template defaults | JVM tests for normalization and lifecycle gating |
| Recording | Existing MP4 library and markers retained; Media3 Transformer performs local trim/export; safe trim-plan validation remains the guard | JVM tests validate invalid ranges; physical-device media-file testing remains required |
| Audio | Existing RootEncoder echo/noise controls retained; advanced DSP profile validation contract added | JVM tests validate DSP bounds; no fake DSP processing is enabled |
| Capability UX | More-tools capability matrix labels local, device-dependent, integration-ready, and service-required features | Static smoke check and UI compile |
| Backup | Existing safe scene-only import/export now carries presentation metadata while continuing to omit credentials | Importer tests cover metadata and secret isolation |

## Intentionally gated capabilities

True simultaneous screen-plus-camera picture-in-picture requires a shared-surface compositor that owns both input producers and one encoder output. The current RootEncoder path safely supports one active video source, so the release exposes a compositor contract and capability status rather than enabling an unverified media path.

Multi-track recording and chapter-aware post-session editing still require additional media composition work. The release now includes a real Media3 Transformer trim/export path for local MP4 files, while the `RecordingEditor` contract keeps multi-track and chapter muxing explicit until those behaviors are verified on device.

Advanced audio mixing, noise gate, compression, equalization, and limiting still require DSP processing before RootEncoder’s encoded audio path. The release validates a future profile and keeps existing hardware/provider-supported microphone processing active; Media3 audio processors are available for local edit/export workflows but are not silently inserted into live capture.

OAuth chat, events, moderation, metadata, scheduling, cloud backup, remote control, SRTLA/RIST bonding, and USB/UVC capture remain behind provider, relay, pairing, or hardware contracts. The capability matrix names those requirements directly.

## Architectural decisions

The enhancement does not add a second encoder for each destination. Direct multistream remains bounded to two RootEncoder `MultiStream` slots sharing one encoded media pipeline. Aggregate lifecycle handling is retained until callback identity and independent retry semantics are verified on physical devices.

Analytics are deliberately outside the media hot path. The service records one bounded summary after a completed session and retains the existing history store for compatibility with the current Library UI. No destination URL, stream key, OAuth token, or cloud identifier is stored in the analytics table.

Scene metadata uses defaulted fields so v0.4.2 JSON remains readable. Imported groups are filtered to valid source IDs, transition durations are bounded, and scene-only import never modifies encrypted destination credentials.

## Validation required after build

The sandbox can run static checks, JVM tests, lint, and APK packaging. A physical Android test is still required for long-duration screen and camera sessions, camera switching, two-destination fan-out, SRT listener interoperability, SQLite persistence after process death, notification actions, and thermal/battery behavior. YouTube, Twitch, and Kick ingest should be tested with disposable or rotatable stream keys.
