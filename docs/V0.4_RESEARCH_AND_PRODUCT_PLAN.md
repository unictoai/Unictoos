# Unictoos v0.4 research and product plan

## Product direction

Unictoos v0.4 is a professional **mobile broadcast control room**, not a desktop OBS clone. The product should make one high-quality stream dependable first, then add richer creator workflows around that stable media path. The app’s differentiator is a calm mobile workflow: configure a destination once, verify the device before going live, compose a scene without a dense desktop mixer, observe health in real time, and recover transparently when the network or device changes.

The release must separate what is production-ready from what still requires a backend, platform OAuth, a self-hosted relay, or physical-device certification. A professional app earns trust by exposing those boundaries instead of showing disabled features as if they already work.

## Research comparison

| Project | Strongest relevant pattern | What Unictoos should adopt | What Unictoos should not copy blindly |
|---|---|---|---|
| [RootEncoder](https://github.com/pedroSG94/RootEncoder) | Android capture/encoding with RTMP, RTSP, SRT, UDP, screen capture, filters, and multiple protocol clients | Keep the encoder behind a session-owned adapter, preserve explicit release boundaries, and expose truthful capability checks | Replace the current verified 2.8.0 integration without an official stable migration path |
| [StreamPack](https://github.com/ThibaultBee/StreamPack) | Modular Android broadcaster with RTMP/RTMPS/SRT, Camera2/MediaCodec, custom sources, metrics, and careful stop ordering | Separate capture, transport, metrics, and reconfiguration; serialize encoder changes | Introduce a second capture engine during the graphics-stability remediation |
| [OBS Studio](https://github.com/obsproject/obs-studio) | Mature separation of sources, scenes, transitions, encoders, recording, outputs, and plugins | Use clear source/scene/output seams, duplicate-source protection, and explicit failure reporting | Copy its desktop UI or assume mobile hardware can sustain desktop-style composition |
| [StreamCaster Android](https://github.com/alxayo/StreamCaster-android) | RTMP/RTMPS/SRT matrix, encrypted profiles, QR import, service-owned state, per-session encoders, serialized reconfiguration, CI release builds | Store credentials securely, start services with profile IDs, validate protocol/codec capability, and automate release checks | Advertise experimental SRT modes or OAuth features without their backend and tests |
| [ScreenStreamerGo](https://github.com/dimadesu/ScreenStreamerGo) | Small Android screen broadcaster with RTMP/SRT, H.264/H.265, AAC/Opus, releases, and explicit roadmap gaps | Keep protocol and codec support visible and honest; publish installable APKs | Treat adaptive bitrate, audio routing, or reconnect as complete merely because the UI mentions them |
| [LifeStreamer](https://github.com/dimadesu/LifeStreamer) | Android IRL streaming with USB/UVC sources, foreground/background mode, adaptive bitrate, reconnect, source switching, and rotation fixes | Add capability-gated source switching, background policy, and device/rotation test matrices later | Add UVC, bonding, or indefinite reconnect before the primary capture path is certified |
| [Moblin](https://github.com/eerimoq/moblin) | Extensive mobile protocols, bonding, adaptive bitrate, remote control, telemetry, localization, and multiple sources | Prioritize operator telemetry, quality presets, remote-control contracts, and source capability discovery | Claim iOS-style bonding or multi-protocol parity without Android implementation and field testing |
| [Owncast](https://github.com/owncast/owncast) | Self-hosted video plus chat, modular streaming engine, metrics, security validation, federation, and dependency automation | Keep a future relay/self-host seam and structured diagnostics | Build a server, chat, or federation layer into the mobile release without backend scope |
| [MediaMTX](https://github.com/bluenviron/mediamtx) | Protocol conversion, forwarding, authentication, hooks, metrics, and multi-protocol ingest/playback | Recommend an optional relay for stable multistream fan-out and ingest monitoring | Duplicate three encoders on-device and call that a reliable relay architecture |

## v0.4 implementation priorities

### 1. Operator-grade go-live readiness

Before the user presses Go Live, the Studio screen should show destination, network, microphone, capture source, and selected quality as a compact checklist. A blocking check disables the start action and explains the exact next step. Service-side validation remains authoritative; the UI is a fast preflight, not a security boundary.

### 2. Deterministic session ownership

The streaming foreground service remains the sole owner of the live session state. Each start gets a generation. MediaProjection is one-shot per session, preview surfaces carry identity tokens, encoder preparation is serialized, all encoder changes are serialized, and stop/release is terminal before a new pipeline is admitted. This follows Android’s requirement that each projection session requires fresh consent and that a projection token/instance cannot be reused for multiple virtual displays.[1]

### 3. Honest destination profiles

Destination profiles should eventually be stored and launched by profile ID, with stream keys loaded only inside the service from encrypted storage. RTMP, RTMPS, and future SRT settings should have protocol-specific validation and security warnings. QR import belongs in a later slice with strict schema and credential redaction.

### 4. Quality and health controls

The default profile should remain a conservative mobile profile. High-load profiles should show a caution before start. Live telemetry should show elapsed time, bitrate, FPS, thermal state, network transport, reconnect attempts, and clear degraded/recovered messages. Adaptive bitrate must be bounded, serialized, and tested against actual encoder support.

### 5. Professional but mobile UI

The UI should keep three primary destinations in the bottom bar, use the Studio as the main operator surface, keep setup in a compact settings flow, avoid desktop mixer density, and favor stable layouts over decorative animation. Stream-key fields should be masked by default. Loading states must have bounded timeouts and clear recovery actions.

## Explicitly deferred from v0.4

True simultaneous YouTube/Twitch/Kick fan-out remains deferred until a relay or independently validated per-destination runtime exists. The current RootEncoder MultiStream adapter is a foundation, not proof of production multistream. UVC cameras, SRTLA/RIST bonding, OAuth chat/moderation, platform metadata APIs, cloud backup, and remote control require additional backend or hardware certification work.

## Release acceptance

A v0.4 release is acceptable only when unit tests, lint, static smoke checks, debug packaging, Android-test packaging, and R8 release packaging pass. Physical acceptance additionally requires long-duration streams on the Infinix X6853, repeated preview and capture recreation, Fix/retry recovery, Activity recreation, microphone/camera switching, network handoffs, and destination-side ingest verification.
